# Framework conventions

- This repository is `crabphp/framework`. The networking engine lives in `src/Engine/` with its own `composer.json`, kept able to be published alone as `crabphp/engine`, and for now released only inside the framework, which `replace`s it; framework components are sibling namespaces under `src/`.
- Nothing under `src/Engine/` may reference a `Crab\` namespace other than `Crab\Engine\`; `tests/EngineBoundaryTest.php` enforces this. The framework may depend on the engine, never the reverse.
- Engine tests live in `tests/Engine/`, engine benchmarks in `benchmarks/`.
- [ARCHITECTURE.md](ARCHITECTURE.md) is the agreed design: layers, lifecycle, scopes, concurrency model and build order. Read it before designing a component and keep it true when the design changes.
- [COMPONENTS.md](COMPONENTS.md) is the flow for building a component. Follow its steps in order and meet its definition of done; when the flow itself changes, change that file in the same change.
- [docs/](docs/documentation.md) is the guide for application developers. A change to what an application developer writes, runs or configures changes its page in the same piece of work; the `sync-docs` skill (`.claude/skills/sync-docs/`) says how the pages are written and checks them against the code.
- When a convention is decided or changed, record it in this file in the same change. Before adding a class, interface or helper, check it against these rules and against how the existing components already do it.

## Lean and standard

- Keep the framework lean. Prefer a small implementation of our own to a third-party dependency; runtime dependencies are Revolt (for the native loop backends) and the PSR interface packages. Ask before adding any other.
- Everything is used through a `Crab\` type, so that nothing we depend on is outside our control and Crab always has a place to add a method. A third-party library is wrapped behind our own interface in one place, and only that place names it. A PSR interface is extended by a Crab contract, never asked for bare by Crab's own services.
- Async tools come from `Crab\Engine`: `EventLoop`, `Suspension`, and `Async\Pool`, `Task`, `Async` and `Cancellation`. Only `src/Engine/EventLoop/` may name Revolt; `tests/EngineBoundaryTest.php` enforces it for all of `src/`.
- Follow PHP-FIG wherever a PSR exists: PSR-7 messages, PSR-17 factories, PSR-15 handlers and middleware, PSR-11 container, PSR-3 logger, PSR-14 events, PSR-16 cache, PSR-18 client and PSR-20 clock.
- Use the multiline docblock rule from the engine conventions in framework code too.

## Components

- Each component has its own folder and namespace under `src/` (`Http`, `HttpClient`, `WebSocket`, `Broadcast`, `Routing`, `Validation`, `Auth`, `Container`, `Config`, `Log`, `Clock`, `Console`, `Database`, `Cache`, `Storage`, `Events`, `Queue`, `Schedule`, `Testing`) and its tests in the matching folder under `tests/`.
- Every component has the same shape: it works standalone, has a contract when packages touch it, ships a `<Component>Provider` when it is optional, and is kept able to be published as its own package the way the engine is.
- A component works on its own, without `App`, the container or a provider. It may depend on `Contracts`, on PSR interfaces and on the engine, and on another component only where that is its purpose. `tests/LayerBoundaryTest.php` enforces this; a new dependency between components is added to its `ALLOWED` list deliberately, never worked around.
- The root of `src/` is the glue that makes components an application: `App.php`, `AppBuilder.php`, `Server.php`, `Route.php`, `Command.php`, `helpers.php`, and `Commands/` for built-in commands. Code that needs `App` belongs there, not inside a component.
- Do not add a `Support` or utility namespace until two components need the same code, and then put only that code in it.

## Contracts

- A package depends on `Crab\Contracts` and PSR interfaces only, never on a component's class. So everything a package touches has a contract in `Crab\Contracts\<Component>`, never inside the component, including where no PSR exists: `Config`, `Router`, `Console`, `Container`, `Database`, `Connection`, `Query`, `Schema`, `Table`, `Column`, `Migration`, `Migrator`, `Migrators`, `Validator`, `Rule`, `Clock`, `Logger`, `Factory`, `Middleware`, the HTTP client's `Client`, `Response` and `CookieJar`, `Identity`, `IdentityResolver`, `TokenStore`, `PasswordHasher`, `MiddlewareStack`, `Provider`, `WorkerProvider`, `Runner`, the cache's `Cache` and `Store`, the storage's `Storage`, `Disk` and `Drivers`, the events' `Dispatcher`, the queue's `Queue` and `Store`, the schedule's `Schedule` and `Task`, and the console's `Command`, `Input` and `Output`, and the router's `Urls`, `DeclaredRoute` and `RouteGroup`.
- Anything an application can do through `App`, a provider can do through a contract in the container. When `App` gains a way to extend the application, the contract comes with it.
- Exceptions and immutable value objects are the exception to that: `HttpException`, `DatabaseException`, `ValidationException`, `Cookie`, the `Response` factories and the validation attributes (`Email`, `Length`, `ListOf`, ...) are named by class, because there is no behaviour behind them to swap.
- A value object that a contract returns or takes lives beside it in `Crab\Contracts`, as a final readonly class with no I/O (`Contracts\Database\Page`, `Contracts\HttpClient\File`, `Contracts\Queue\Message`), since a contract may not name a component's class.
- `App` binds each contract in the container, and binds the concrete class to the same object so that asking by class cannot autowire a second one. The glue type-hints contracts too.
- Every service has a contract of Crab's own, including where a PSR interface covers it completely: the contract then extends the PSR interface and may add nothing (`Contracts\Log\Logger`, `Contracts\Clock\Clock`, `Contracts\Http\Factory`). It is the name applications ask for and the place a method is added when Crab needs one. `App` binds the contract and binds the PSR interface to the same object, so code written against the standard gets it too. What an application implements has one too where it is something Crab runs: `Contracts\Http\Middleware` is PSR-15's middleware under Crab's name.
- A contract references only PSR interfaces, other contracts and engine types, never a component's class. The component's class implements the contract and shares its short name (`Crab\Http\Request` implements `Crab\Contracts\Http\Request`).
- Signatures accept the PSR type wherever PSR methods suffice, so third-party implementations plug in; ask for a Crab contract only where its extra methods are used.

## Application wiring

- `App` binds the core directly: configuration, container, validator, router, HTTP factory, logger, clock, error handler and console. The framework's providers are the list `App::PROVIDERS`, applied by `App::configure()`: Database, Auth, Cache, Storage, Events, Queue, Schedule, HttpClient, Broadcast, in that order. An application names its own providers and those of its packages with `withProviders()`, after the framework's; `remove:` leaves out a framework provider and `only:` replaces the list. A concrete way of doing something (`TokenAuthProvider`) and every package stay opt-in. Nothing is found by convention, and `new App()` used directly registers no providers.
- A provider has `register(Container $container)`. There is no `boot()`; bindings are closures run on first use. A provider with work to do in each worker implements `WorkerProvider` as well: `start(Worker $worker, Container $container)` opens what holds a socket, file or timer and `stop(Worker $worker, Container $container)` releases it. Providers stop in reverse order, `stop()` must not suspend, and a provider keeps no state of its own.
- A provider declares its settings, their defaults and what each takes once, with `Config::defaults($section, $values, $rules)`; code reads them with no default argument. Every setting has a rule, written as JSON Schema arrays so that a provider names no component class, and a section with rules takes no other keys (`'*'` lets them through, as `app` does). `Config::check()` runs them all before anything serves or works (`App::runtime()`, `run()`, `runAll()`, and `start`, `reload`, `restart` and `queue:work` before they act), and the factory that makes a component's service checks its own section with `check('<section>')` first. A problem is one sentence, `key is value; it takes what.`, with every problem said at once, a secret's value never repeated, and the console printing it without a trace (`Contracts\Config\InvalidSettings`). A setting is not checked again by hand where it is read; a check between settings (a socket limit against the server's) stays where both are read. `tests/Config/SettingsTest.php` makes a wrong value for every rule; a new setting is covered by it. The container has no per-request scope: `singleton()` is one per worker, `bind()` is new on every `get()`.
- A service known by two names is bound once under its contract and the other name is an alias of it, eagerly made services included.
- Every error response is built by `Http\ErrorResponse`, for the error handler and for the router's 404 and 405 alike. Expected answers such as an unmatched route are returned as responses, not thrown, so they pass back through middleware. The response carries its `Problem`, which an application's `ErrorRenderer` writes in its own format after all middleware; build error responses with `ErrorResponse::make()`, never by hand, so they stay the renderer's.
- Inside a worker, PHP warnings and notices are thrown as `ErrorException`; code must not rely on a warning being ignored, and uses `@` only where a failure is then checked by return value.
- Anything that adds work to every request and is not needed to answer it, such as the request id or CORS, is off by default: it is middleware an application adds, with its measured cost documented.
- CORS declares `Vary: Origin` on every answer whose headers depend on the origin, absent and refused origins included, and keeps any `Vary` already set.
- A route the framework adds, such as the health path, is asked for in `app.php` (`withRouting(health: '/up')`) and shows in `route:list` like any other. `App` adds none by itself.
- A command is named `area:action`, with the area in the singular: `route:list`, `schedule:work`, `queue:retry`, `cache:clear`, `make:migration`. The command that lists what a component holds is `<area>:list` (`route:list`, `schedule:list`); a new component that holds a list gets one. A bare name is only for the application itself (`dev`, `start`, `stop`, `reload`, `restart`, `status`), for the console's own `list` and `help`, and for `migrate`.
- A console option that takes a value is given as `--name=value`; one given without `=`, or with a value of the wrong form or range, is refused before anything runs (before stopping a server or writing a file), naming the option and showing a valid invocation. Every command entry point is checked this way, restart, reload, selectors, comma-separated lists and generators included, and its test shows that an invalid value touches nothing. Report a supplied value-taking option with no value before checking other option values or positional arguments. A raw environment or option value stays raw until the reader that owns it checks its whole form and range. A generator checks every write, stub included, and reports success only once the final file is as intended.
- Nothing fails silently outside a request: `App` sends everything the engine catches in a worker (a failed task, a failure escaping a timer, a failing `stop()`, a request failure that escaped the error handler) to the logger through the engine group's `onFailure()`, and the worker keeps running. A new entry point (queue job, scheduled job) gets the same treatment.
- What is logged about a request is its method and path, never its query string. `app.debug` is read as a validated boolean, so an unrecognised value never shows an exception's details.
- An exception's trace is written without call arguments, in the log, the engine's failure reports, process-control logs and the debug page, whatever `zend.exception_ignore_args` says: an argument can be a password. All of them render through `Engine\FailureReporter::describe()` and `frames()`; there is no second formatter. A test of this enables argument capture in its own PHP process, never relying on the host's php.ini.
- A response cookie with a positive lifetime is sent with `Max-Age` alone; one being removed has `Max-Age=0` and the fixed 1970 `Expires`. `Cookie` stays a value object and never reads the clock.
- `App` assembles its middleware, the error handler included, in each worker as the worker starts, never in the parent and never lazily on a request, so a misconfiguration stops startup with its cause printed.
- Before anything serves or works, `App::unmade()` follows, without making anything, what the container must make for unattended code: each route's action and named middleware, every listener, every scheduled task, job and command. A problem stops `runtime()`, `run()` and `runAll()` as a `Contracts\Container\MissingServices`, every one at once, each sentence saying where the entry is named; `describe` lists them. A new place that names a class for the container to make later (a registry of handlers, a new kind of scheduled work) reports its entries to `unmade()`. A command typed at the console is not checked: it fails in front of whoever typed it. The walk never constructs or runs a closure: constructor work is not checked, by design.
- A binding's closure and a constructor the container calls must not suspend: the container is shared by every fiber in the worker and guards against circular dependencies by entry name, so a second request asking for an entry that is still being made is refused.
- Objects the container keeps are shared by every request a worker serves: they hold no state of a single request, and anything holding a socket or file is made in the worker on first use, not in the parent.
- State has three scopes. Process scope (config, routes, provider list) is fixed once the application is defined. Worker scope is the container's kept objects. Request scope travels only on the PSR-7 request and its attributes, never in a service or a static.
- A component that does I/O (database, cache, queue) exposes a pool in its contract, `acquire()` and `release()`, so code written against it is correct with blocking drivers now and async drivers later. Blocking drivers ship first. The pool is the engine's `Async\Pool`; do not write another. A store that keeps its entries in the database (`Cache\DatabaseStore`, `Queue\DatabaseStore`) takes a `Connection` and so borrows from the database's pool; it has none of its own. A store with a socket of its own, such as one for Redis, will have a pool. The HTTP client keeps its pools to itself, one per server: a call is one request and its answer, and there is nothing for a caller to hold between two.
- A pooled component resolves the event loop when it is used, not when it is constructed: a worker installs its own loop after the fork, and anything that kept the parent's would wait forever.
- When an internal mechanism is replaced, its unused interface methods, constructor arguments and fixtures go with its last caller.
- A connection remembers the database and pool it was borrowed from, across close and replacement, and returns to that pool, which refuses a return that is not its own before any cleanup.
- HTTP, queue consumers and the scheduler run as separate engine worker groups. Workers hold nothing another worker needs; shared state lives in external stores behind contracts.
- Worker processes that serve no requests are run through `Contracts\Runner`, which `App` implements: each worker starts and stops the worker providers and reports failures as an HTTP worker does. A component's command asks for `Runner`; it never builds an engine `Runtime` itself, and never names `App`.
- `start` is HTTP alone unless `server.with` switches more on, so that developing an API starts no job and no scheduled task behind the developer's back; production switches them on from `.env`. What can be switched on is registered by providers through `Contracts\Servers`, each under an id (`queue`, `schedule`): with `add()` it joins the server as `Contracts\Workers` groups, with `command()` or `process()` it is a process a worker starts, stops with SIGTERM and starts again. Registering an id again replaces it. `App::runtime()` is the one place that builds the server's runtime, so the foreground, the background and the watched server all run the same groups. A new long-running part of the framework keeps a command of its own for running apart and registers itself as a server; it does not get a second server command.
- What is declared before the workers start and read in every worker, such as event listeners and scheduled tasks, is held by an object its provider makes in `register()` and binds with `instance()`, so that every later provider can add to it. What such a list names by class is made in the worker, on first use.

## Actions

- An action says what it takes in its signature, and the framework validates the request against it before calling it. Do not add a second place to describe a route, such as an annotation or a schema file.
- Each parameter of an action says where its value comes from, and a value is read from that one place: the pattern's parameters by name, the query string by `Routing\FromQuery`, the body by being a class or a described `Validation\Data`, the request and the user by their type. Do not read a field from wherever it may be, as Laravel's `input()` does: a body's field must not be settable from the address. The body is always one object, an input class or a `Data` described with `#[Fields]`, and never one parameter per field; the query string is either fields marked one by one or one marked object, never both. `GET`, `HEAD`, `DELETE` and a socket upgrade have no body, and an action of one that takes a body is refused when the route is added. Validation problems are reported under the part they were in, `fields` for the body, `query` and `path`, since one name may be in two parts. Everything is read when the route is added and validated the same way; do not add structural validation that runs inside the action. A check that needs the database or the user, such as "this email is not taken", belongs in the action. Services are never action parameters; an action class takes them in its constructor.
- Every parameter of an action has a type, and one without is refused when the route is added. What arrives as text (a query string, a route parameter, a form) is read as the type asked for; JSON is taken as it says. A value is never quietly made another: a number past what an integer holds and a date the calendar does not have are refused. A `Validation\Data` holds only what was sent, so that an update can tell a field left out from one sent as null. Presence and null are apart, as in PHP: a field without a default must be sent, even when it may be null (`?string $note`); a default makes it optional, and in `#[Fields]` a name ending in `?` does. Do not make a nullable type mean optional. Unknown fields are ignored unless the input is `#[RejectUnknown]`; a check across fields is an `ObjectRule` attribute on the class or the described `Data`, pure, never one that reads the database. A union is validated only when it is of the scalar types int, float, bool and string, and JSON's value says which; text stays text where string is one.
- Who made a request is `Request::ip()`: the connection's address, and a proxy's word for it (`X-Forwarded-For`) only through `Http\TrustedProxies` and only from the proxies it names. Do not read forwarding headers anywhere else.
- An address is one form wherever it is read: an IPv4-mapped IPv6 address (`::ffff:192.0.2.7`) is its IPv4 address in `Request::ip()`, `TrustedProxies` and `RateLimit`, however it is written: each reads it from its packed bytes, never from its text.
- A job that follows a write is pushed with `Queue::within($transaction)`: stored by the transaction itself when the jobs are in its database, and otherwise pushed by `Connection::afterCommit()`. Do not push inside a transaction any other way.
- A count shared by workers is `Cache::increment()`, which every store does as one step; never get, add one and set. `Http\RateLimit` is built on it. Middleware written with options that also needs a service implements `Contracts\Http\UsesContainer`, and does not reach for a global.
- Take a body as an input class when its fields are many, nest, or are shared by several routes, and as a described `Data` when it is small. An input class is a final readonly class whose constructor declares every field with one type. A file is a field of the body, never a parameter of its own.
- What a route points at is called an action, in the code, the guide and the skeleton (`app/Actions/`). "Handler" is kept for the PSR-15 interface and what implements it: the router, `ActionHandler`, the error handler, the `$handler` a middleware is given.
- A class the framework calls for the application does its work in `handle()`: an action, a job, a listener, a scheduled class and a command alike. Do not accept `__invoke()` beside it. A route given a class name treats it as an action when it has `handle()` and is not a PSR-15 `RequestHandlerInterface`.
- An action is a class with `handle()`, named verb first after what it does (`ShowUser`, `CreateOrder`), a closure, or `[SomeClass::class, 'method']`. It is a plain class: there is no base class and no helper to inherit.
- An action returns data, which is sent as JSON with 200, or a response when the status, a header or the body needs saying. Status and headers are set in code with the `Response` factories and nowhere else, so nothing has to be kept in step. Do not add an attribute for something code can say.
- Crab writes no description of the API (OpenAPI, JSON Schema). It was built and removed: keeping a document true cost every later feature a second thing to maintain, and a document that is partly true misleads. The signatures are the description. Do not add one back, or keep data on a route or a rule for one, until the owner asks.
- Attributes are for what PHP cannot say in a type: validation rules, and `#[ListOf]` for what an array holds.
- Routing is declared by method chaining, never by named options: a route method declares one route and returns it as `Contracts\Routing\DeclaredRoute`, on which `->name()` and `->middleware()` say more; a group is `Route::prefix()` or `Route::middleware()`, further steps, then `->group()`. Each route is one statement; routes are never chained onto one another. A name is unique, a route has one, and groups add nothing to it. `Router::path()` writes a named route's path and `Contracts\Routing\Urls::to()` its full URL from `app.url`, never from the request, so that a job writes the same links an action does.
- A signature is read when the route is added, never on a request, and one that cannot be honoured throws there, naming the route and saying what to do instead.
- A route keeps the action it resolved for the worker's life, even when the container binding is `bind()`: an action holds no request state.
- Data that does not fit is a 422 built by `Http\ErrorResponse` with every problem by field, returned and not thrown. JSON is taken as it is; only text sources (query string, route parameters) are converted to numbers and booleans. Fields an action does not declare are ignored and never reach it.
- `Validation` knows nothing of HTTP or routing, except PSR-7's `UploadedFileInterface` as a type. A rule is an attribute implementing `Contracts\Validation\Rule`, which checks a value and says what is wrong with it.
- An uploaded file is a field typed `UploadedFileInterface`: the router puts a form's files among its fields, an empty file input counts as absent, and a route read from the query string refuses one when it is added. Its kind is read from its content (`MediaType`), never from what the client claims. On a list of files, `FileSize` and `MediaType` hold for each file and `Length` for the list.
- A rule that cannot read a value refuses it with a message; it never treats an unreadable value as empty. `Pattern`'s `$` is the end of the text. A `float` refuses a value that is not finite, and a date accepts only the forms its message names (`2026-01-31`, `2026-01-31T12:00:00Z`), never a relative phrase such as `now`.
- A typed list's `Length` bounds are checked after its shape and before any item is validated or made, so an oversized list costs one error, not one per item.
- An action's input class, and every class inside it, is read when the route is added (`Validator::inspect()`), so one that cannot be validated stops startup.

## Running the server

- `dev` is for the developer: it watches and restarts. `start` is for production and never watches; it takes `--daemon`. Watching does not come back to `start` as a flag or a default.
- `<command> --help` and `-h` describe a command and never run it; the console handles them, so a command does not use `h` for an option of its own.
- `Server` in the glue is the one place that starts and replaces the application's server, and `ServerFiles` the one place that finds, reads and stops a running one; a command about the server calls them and holds no process logic of its own.
- New code is loaded by a new process, never into a running one: classes cannot be redefined, and the application is defined in the server process before it forks. Do not add a way to "reload" that keeps that process.
- A background server is a keeper, a server process under it, and workers under that. The keeper owns the listening socket and passes it to each server process it starts, so that old and new accept from one queue. Do not make two servers bind the same address instead (`SO_REUSEPORT`): on Linux, connections queued on the socket that closes are lost.
- The keeper stays small and loads nothing of the application, because it runs old code for as long as the service lives. What a reload needs to know travels in the request, not in the keeper.
- `status` and `stop` need nothing of the application: they act through `ServerFiles`, from the files a server keeps, and `Cua` runs them when `app.php` cannot be loaded. A new command that only reads or stops a running server does the same and joins `Cua::WITHOUT`; one that needs the application's code never does, since what it would run is what failed to load.
- A command that starts or reloads a server returns only when it accepts connections, and exits with a failure and the reason when it does not. A reload that fails leaves the running server untouched.
- A process that stops gracefully goes on reading a connection that looks idle for a moment (`HttpSession::DRAIN_GRACE`): the client may have sent a request before it could know.
- A process id read from a file is checked to be a server before it is reported or signalled; the file may be older than the process that now has the number.
- `server.drain` is the seconds a worker has to finish requests in hand when it stops; the worker passes that number down to its connections, so no shorter timer cuts them first. At the limit it logs one warning with how many requests it cut, counted by the protocol (an idle keep-alive connection is not one), and that line reaches stderr if the logger fails. A group with its own allowance borrows nothing from another group, and a supervisor that has to end a worker says so once.
- A generation keeps the allowance it started with. The keeper enforces a retiring generation's deadline in one collection pass that also runs while another generation starts or fails to start, and writes the allowances beside the pid file so that `stop` waits as long as the running server needs, whatever the configuration on disk now says. `--timeout` given by hand always wins.
- `stop --force` ends the whole server: through the owners first, then, if the keeper does not answer, with one signal to the keeper's process group, and only when the keeper leads its own session, which a server in the background makes it do; a program registered with `Servers::process()` stays in that session so the signal reaches it. Otherwise only the keeper is ended and the command fails, saying so. Never signal a group built from pid 1 or less. Do not keep lists of worker pids to signal later: a number outlives its process.
- The keeper writes when it was started beside its pid; a pid that is alive but was started at another time is a stale file, and nothing is signalled. A plain `stop` returns when the keeper's session is empty, or fails naming what is left.
- A running server says how it is doing through one file per server in the stats directory, beside the pid file, which the server process alone writes: workers report their `stats()` over the control pipe about once a second, and the supervisor writes the file at once when a worker starts, is ready, retires or dies, and otherwise once a second. `status` reads the files and removes those whose process has gone. Workers do not write files of their own, and nothing on the request path does more than `Worker::count()`.
- What a worker handles is counted with `Worker::count()` where it is handled, under a plural name: `requests` in the HTTP handler, `jobs` and `failed` in the queue consumer, `runs` and `failed` in the scheduler. A component that handles a new kind of work counts it the same way.
- After going into the background a process must not use the `STDIN`, `STDOUT` or `STDERR` constants, which are closed; `echo`, `php://stdout` and `php://stderr` reach its log.
- A program registered with `Servers::process()` runs under a shell, which does not pass a signal on. To stop it the worker looks up the shell's descendants at that moment (`/proc` on Linux, `ps` elsewhere), signals them deepest first and then the shell, and waits until their output is closed. No shell wrapper, and no extra package on the server.
- A test that waits from the main context (`Task::await()`, a fake client's retry) runs the loop to its end before it returns, so the next test can install its own.
- A process started with `proc_open` inherits every descriptor its parent has open, and PHP cannot close them by number. So only a process that opens almost nothing, the keeper, may start a long-lived one; a server process must never start its own successor.
- Process control that is not about HTTP (`Keeper`, `Generation`, `Daemon`, `PidFile`, `FileWatcher`, `Runtime::onReady()` and `onSignal()`) lives in `Engine\Process` and is tested there with real processes; what needs `App` lives in `Server`, tested by driving a real application in `tests/ServerTest.php`. Run both on Linux (`composer test:linux`) before changing either.

## Middleware

- There is one kind of middleware, PSR-15's, used through `Contracts\Http\Middleware`, and two places it goes: around every request, with `withMiddleware()` in `app.php`, and around some routes, with `->middleware()` on a route or a group. The same class works in both; nothing about a class says where it may be used.
- The framework's own middleware around every request is the list `App::MIDDLEWARE`. An application can put its own before or after it, leave one out, or replace the list; do not hard-wire a middleware into `App` so that it cannot be moved or removed.
- A feature that runs around requests is middleware an application adds, not a configuration switch: one place says what runs around a request. `RequestId` ships and is not in the default list.
- A middleware is told its options through its constructor and given as an object. Do not parse options out of a string such as `'throttle:60,1'`.
- All middleware is made when a worker starts, the application's and every route's, never on the first request. A route's or a group's middleware that could never run, a name that is no class or a class that is no middleware, is refused where it is declared, naming the route.
- The same name or the same object given again to a route, by its groups or itself, runs once, at the later place. Two objects of one class both run: each has its own options, and dropping one could drop a check the application asked for. Do not remove middleware by class.
- A route records the middleware around it in `RouteInfo`, and `route:list` lists it, so what guards a route can be read without opening the routes file.
- A middleware object may be made before the workers are forked, so it chooses nothing per worker in its constructor (`RequestId` picks its prefix on the first request).
- An application sets the middleware around every request with `withMiddleware()` and a provider adds to it through the `MiddlewareStack` contract. `App` has no method of its own for it.
- `Http\AccessLog` writes one line per request and never changes the outcome: a failure of its own goes to the engine's `FailureReporter`, and the response or exception passes through as it was.
- `Http\Concurrency` is how a worker is kept from working on every request at once: middleware an application adds with a number of its own, around every request or around a route. A request that waits has run none of the application's code; one that waits past `wait` is answered 503 by `Http\ErrorResponse`. Do not add a `server.*` setting or a default limit for it.
- A way of doing something for some routes, such as authenticating, is a middleware. Do not add a contract and a wrapper middleware around it where PSR-15 already says the same.

## WebSockets

- A socket route is declared with `Route::websocket()` and needs no provider: the capability costs an application nothing until a socket route exists. Its settings are checked at startup with every other.
- The action is one long `handle(Socket $socket, ...)`. It starts inside the HTTP request and the 101 goes out at its first use of the socket, so what it throws before that is an ordinary HTTP answer; after that a failure is reported once and closes with 1011.
- One action object serves every connection of its route in a worker. Connection state lives in locals of `handle()`, never in properties.
- Text arrives as it was sent (`array` for JSON, otherwise `string`); only binary is wrapped, in `Binary`. Do not wrap the ordinary message.
- Everything a connection can hold is bounded: the inbox (16 messages, 256 KiB, which is also the ceiling of `websocket.max_message`), the time an action may leave a full inbox untouched, the wait for a slow client, the connections per worker.
- The end of a connection is not a failure: `SocketClosed`, and a cancellation caused by the socket's own token, end an action quietly. Any other exception is reported.
- A test's sockets belong to its `Testing\Api`, which closes them and waits for their actions to settle. A helper that leaves an action or a loop running is a defect.
- In the engine, a session's silence clock runs only while we read: a pause of ours never retires a peer, so whoever pauses reads bounds that pause.

## Broadcasting

- `Storage` keeps files on named disks: `local` and `memory` in the framework, `s3` in `crabphp/s3`, added through `Contracts\Storage\Drivers` with the settings it takes. Every disk checks paths with `Contracts\Storage\Path` and writes a file whole or not at all. A disk that talks to a service goes through the HTTP client, never a blocking SDK. Media models, image processing and quotas are the application's.
- `Broadcast` follows Cache and Queue: the mechanism in the framework, a `Carrier` behind a contract, the Redis carrier in `crabphp/redis`. It costs nothing until a socket joins or something sends.
- A socket joins through `Contracts\WebSocket\Channels`, handed over by the glue. The `WebSocket` component never names `Broadcast`.
- A message is encoded once, before the carrier. Fan-out writes in bounded batches, yields between them and never waits for a reader.
- Delivery is at most once, in order per sender and channel, with no replay. So a client must never be left silently stale: a lost subscription closes every joined socket with 1012 to make it reconnect and refetch.
- A client is slow when it stays behind, not at its first full buffer: a bounded backlog per recipient, then 1008 at the bound or after `websocket.send_timeout`. A recipient that keeps up costs no backlog and no timer.
- A cleanup that walks many recipients continues past one that fails, and reports that failure.
- `local` reaches this process only. Startup refuses it where another process could send, and a sender outside the serving process fails with a message rather than sending to nobody.
- `within($transaction)` is the queue's hand-off: sent after the outermost commit, and a failure then is reported, never thrown into the committed caller.
- Every wait in a test that crosses processes, sockets or the loop has a deadline and a message naming what it waited for.

## Calling out

- Code that calls another server asks for `Contracts\HttpClient\Client` and never uses `file_get_contents()`, cURL or a stream wrapper for it: those hold the whole worker until the other side answers.
- The client waits on the event loop: a socket is read and written only when it is ready, and the fiber that asked is suspended meanwhile. It names no Revolt type; its loop is `EventLoop::current()`, asked for when a connection is made.
- An answer with an error status is returned, not thrown. Only a request that got no answer throws, and its message carries the method, host and path, never the query string or a header.
- Without `retry()`, a request is sent again by itself only when the server cannot have acted on it twice: a kept connection turned out to be closed, nothing came back, and doing it twice is doing it once (`GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`); or, on HTTP/2, the server said it did not act on it (a refused stream, or a connection it left before reaching the request). A `POST` is never repeated on a guess.
- What the client does not do is said where an application developer reads it: no HTTP/3, no HTTP/2 without encryption, no server push, no proxy other than a plain HTTP one, and no brotli.
- HTTP/2 is offered to every `https` server and spoken with those that take it; one `Http2Session` per server carries all its requests, and its connection stays lent from that server's pool for as long as it lasts. Every header block received is decoded, wanted or not, because each may change the table the next refers to. Frames are written whole and one writer at a time.
- The HPACK tables (`Hpack::STATIC`, `Hpack::HUFFMAN`) were generated from the text of RFC 7541 and are checked against its examples; do not edit them by hand.
- A limit on an answer counts what it decodes to, not what came over the wire: a header block is bounded by its decoded size, the same 64 KiB as an HTTP/1 head.
- `retry()` tries a request again only when that cannot do it twice: one that may safely be made twice, on no answer or 429, 502, 503, 504; any other only when none of it was sent (`NetworkException::$unsent`) or the server answered 429 or 503. A 500 is never tried again. Widening this needs the owner's agreement.
- `timeout()` bounds the whole call: every try, redirect, connect and pause shares one deadline, and a connect is bounded by `connect_timeout` and by what is left. A pause that cannot fit ends the call with what the last try gave. Nothing is written after the deadline; a request of which no byte was written fails as unsent. A connection is opened by the caller that borrows it, under that caller's deadline.
- A message that quotes a URL the caller gave shows it without its query and fragment.
- A name is looked up with the engine's `DnsResolver`, never `gethostbyname()` directly: the hosts file, then answers kept for as long as they hold, then the name servers over UDP on the event loop. The system's blocking resolver is only what is fallen back on when they give nothing.
- The client an application is given is shared by every request its worker serves, so nothing about one caller is set on it. `timeout()` and `cookies()` return another client over the same connections and leave the first as it was; a new option of that kind is added the same way, never as a setter.
- What belongs to one request is an argument of the call (`query:`, `headers:`, `json:`, `form:`, `files:`, `body:`, `cancellation:`); what holds for several is an argument of the constructor and, where a caller needs to change it, a method that returns another client. One thing is said in one of the two, not both.
- A client keeps no cookies unless it is given a jar. A jar gives a cookie back only where a browser would: host or named domain, path, `Secure`, and not expired; and it keeps a `Secure` cookie only from an `https` answer.
- A plaintext answer cannot replace, delete or shadow a live `Secure` cookie of the same name on an overlapping domain and path; selection and protection use one path-matching rule.
- `Response::throw()` is how an error status becomes an exception, asked for by the caller. Do not add a client-wide switch that makes every error status throw.
- `FakeClient` extends `Client` and replaces only what carries a request (`Transport`), so that a test exercises the real request building, redirects and cookies. It is the one class in `src/` that extends a concrete class; a request no reply matches throws rather than reaching the network.

## Request bodies

- A file in a request is never read into memory by the framework. The engine keeps a large body on disk, `Multipart` reads it through a window, and an `UploadedFile` is a `StreamSlice` of the place the file lies in. Do not turn an upload into a string to parse or to move it.
- What is kept in memory is bounded: a form's fields together, the number of its parts, and the headers of one part.
- A multipart body Crab sends, from the HTTP client or from `Testing\Api`, is written by `Http\Multipart::write()`. `Api` takes a body as the client does (`json:`, `form:` and `files:`, or `body:`, one of them), so a test sends what a client would and it goes through the same parser.
- JSON from outside (a request body, a socket message, an answer the client reads) is refused before decoding when any object has more than 1,000 members, repeated names included, at any depth: a request is answered 413, a socket closes with 1009, and the client's `json()` throws `LengthException`.
- The size a body may be and the time a client has to send it are settings, `server.max_body` and `server.body_timeout`, with the engine's defaults.

## Generality

- Crab is a framework: a component ships the general mechanism, and leaves an application's decisions to the application. It names no header, table, column or storage as the only one.
- A concrete way of doing something is opt-in, behind a provider of its own (`TokenAuthProvider` beside `AuthProvider`), so that an application doing it another way never loads it.
- A component ships no migration of its own. A table it needs is written into the application's migrations by a command (`token:install`), so that the application owns the file and all its tables are in one place.
- Where a choice has a standard default, the default is an argument's default value (`Authorization: Bearer`), and anything else is that argument, never another class.

## Authentication

- Who makes a request is request state. Middleware puts the user on the request's `user` attribute, and it reaches an action as a parameter whose class implements `Contracts\Auth\Identity`. There is no static accessor for it and none may be added.
- A way of authenticating is a middleware and nothing more. Core `Auth` is `Identity`, that convention, and the `PasswordHasher`; it decides no scheme.
- Tokens are one way, opt-in through `TokenAuthProvider`: the `TokenAuth` middleware, the `TokenStore` and the `IdentityResolver` an application binds so that a user can be found from the id a token belongs to. Crab keeps no user table of its own.
- A secret is never stored as it is: a token is kept as its SHA-256 hash and a password through `PasswordHasher`. Neither appears in a log or an exception's message.
- A browser cannot send a header on a WebSocket, so it trades its credential for a ticket: `Auth\Ticket` in place of `TokenAuth` on the socket route, `Auth\IssueTicket` behind whatever authenticates the application. A ticket is random, kept only as its hash with the identity's id, used once through `Cache::take()` and gone after `auth.ticket_ttl`. Every refusal is the same 401, and a ticket that is present but wrong never falls back to another credential.

## Scope

- Crab is a framework for JSON APIs that is long-running by design, not a Laravel on another engine. There is no model layer over the query builder, no session component and no roles or permissions component, and none is to be added without the owner's agreement. Say so plainly where an application developer would look for one.
- Events, cache, queue and scheduling are Crab's own code. A third-party library may stand behind a contract as a store or a driver, wrapped in one place; it does not replace a component.

## Cache

- `Cache\Cache` is the one class that checks keys, works out expiry and turns values into text; a store only stores, behind `Contracts\Cache\Store`. A new place to keep entries is a new store, never a second cache class.
- A store's `add()` sets a key only when it is absent, its `deleteIf()` removes a key only while it still holds the given value, and its `extendIf()` gives such a key a new expiry, each as one step with respect to every other caller of that store. `Cache::lock()` and `Lock::refresh()` are built on them; a store that cannot do all three atomically must not be used for locks.
- A store's `take()` returns a live entry and removes it as one step with respect to every caller. Anything used once is redeemed with it, never with a get and then a delete.
- Under its prefix, a cache keeps values as `value:` keys and locks as `lock:` keys. `clear()` removes this cache's values only, on every store: locks are coordination, not cached data, and another prefix's entries are another application's. `clearLocks()` (`cache:clear --locks`) is the one way to remove locks. A store's `clear($prefix)` removes by key prefix, so the file store keeps each entry's key in its file.
- Coordination that must survive `cache:clear` uses a lock, never a value: `onOneServer()` claims and keeps its runs with locks, and `withoutOverlapping()` holds a lease, a short lock renewed by a timer while the run lasts.
- The file store never follows a link (at an entry, its folder or the cache directory itself), keeps folders `0700` and entries `0600`, and removes an entry by unlinking it before truncating, checking both: the cache unserializes what it reads, so only the server's user may put a file there. Its default directory is the application's `storage/cache` (`app.path`). An application with no base path must set `cache.directory`; no default is ever a shared folder, such as the system temp folder, that another account could create first. An entry that outlived its time stays until it is read or `cache:prune` runs.
- The file store refuses a folder it finds that group or others can write to, or that another user owns (root excepted, which is safe only because the folder is always one the application was configured with), with a message saying `chmod 700`; it never reads an entry another user could have put there.
- Times are passed to a store, never read by it, so that every store can be tested with a frozen clock.
- A cache is chosen with `cache.store`, and anything else by binding `Contracts\Cache\Store` after the provider. There is one cache per application; do not add named caches until the owner asks.

## Events

- An event is a plain object and a listener a closure or a class with `handle()`. Listeners are added in a provider's `register()`, never in a worker and never by a naming convention or an attribute.
- Listeners run in the fiber that dispatched, in the order added, and what one throws reaches the dispatcher's caller. Work that should outlive the request or be retried is a job a listener pushes; do not add queued listeners.
- Before a component dispatches a new event, agree which and what it carries: it becomes part of its contract. An event is dispatched after the store knows what it reports, so that a listener finds things as the event says they are.
- The framework's own events are plain objects beside the contract they concern (`Contracts\Queue\JobRan`, `Contracts\Schedule\TaskRan`), dispatched through PSR-14's `EventDispatcherInterface` when the container has one and skipped when it has none. What a listener for one throws is logged and never changes the outcome of the work it reports. Do not dispatch one on the path of every HTTP request; what watches requests is middleware.

## Queue

- A job is a class with `handle()`: services in its constructor, its data as typed parameters, pushed by name. There is no base class, no interface and no serialized object: the data is JSON, checked against the signature where it is pushed.
- A job is delivered at least once. Nothing in the queue may assume a job ran only once, and the guide says so wherever a job is described.
- A store hands a job to one worker at a time by changing its row, not by holding a lock or a transaction while the job runs. `Queue\DatabaseStore` uses the query builder only, so that the same statements serve MySQL and SQLite.
- A job that was taken and never reported back is given out again after `queue.retry_after` seconds without a renewal. Its attempt was already counted, so a job whose worker dies under it every time is given up on like any other.
- A consumer in a worker renews the job it runs every third of `retry_after` through `Store::renew()`, which holds only for the worker on the try it was given; `retry_after` bounds how long a process may block, not how long a job runs. Release, fail and renew by a worker that no longer holds the job change nothing; complete deletes the job whoever finished it, since the work was done.
- A job's time is bounded cooperatively first: past its timeout (`queue.timeout`, a supervisor's `timeout`, `#[Crab\Queue\Timeout]`) the `Engine\Async\Cancellation` its `handle()` takes is cancelled, and so is it when its reservation was lost. The hard limit is the process: `Worker::deadline()` asks the engine's supervisor to end a worker still running past it, `queue.grace` after the timeout. Do not claim a timer inside the worker can stop blocked PHP, and do not add a signal-based one.
- What a job throws is logged with its trace, as a warning while tries remain and as an error when it is given up on. The consumer's loop catches a failure of the store too, logs it and goes on.
- Retries default to the consumer's settings (`queue.tries`, `queue.backoff`); a supervisor may set its own, and a job may override either one with `#[Crab\Queue\Retry]`, and its timeout with `#[Crab\Queue\Timeout]`. Each attribute is checked where the job is pushed, read once per class, and what it leaves out comes from the consumer running the job. Do not add other per-job options until the owner asks.

- A queue supervisor is a named set of workers with its queues and limits, declared under `queue.supervisors` and read by `Queue\Supervisor`. `queue:work` runs every one as an engine worker group of its own through `Runner::runAll()`. A setting a supervisor accepts must change what its workers do today: do not accept a key ahead of the feature behind it.

## Scheduling

- Tasks are declared on `Contracts\Schedule\Schedule` in a provider's `register()`. There is no static name for it and no schedule file found by convention.
- The scheduler is run by `schedule:work`, on its own, or by `start` as the server `schedule` when `server.with` switches it on: a long-running worker that wakes each minute, and holds a timer for each task set by seconds. Do not add a command for cron to call every minute beside it.
- A named time (`daily()`, `hourly()`) is a cron expression and nothing more; `Schedule\Cron` is the one place that reads one.
- `everySeconds()` is the one kind of time that is not a cron expression: an interval, run by a repeating timer of the engine's loop that `Scheduler::repeat()` starts, counted from when the scheduler starts. Do not add seconds to `Cron`, and do not make the scheduler wake every second to look for due tasks.
- A task due while its last run is still going is skipped and logged, in the worker that runs it. Such a skip is not logged for a task set with `everySeconds()`. Across machines, `onOneServer()` agrees through `Cache::lock()`: on a lock named after the minute for a cron task, and for an interval task on one lock that the server running it refreshes at every run, since servers share no name for such a run. `withoutOverlapping()` extends the skip to every scheduler sharing the cache with a lease the run renews every third of its length; a lease that cannot be renewed is logged, never used to stop the run. A schedule that asks for either without a cache is refused when `schedule:work` starts.
- A minute the scheduler was not running in is not made up for.

## Database

- MySQL and SQLite are the supported databases. PostgreSQL is out of scope for now: do not add code, tests or documentation for it until the owner asks.
- SQL values are always bound, never concatenated; an exception's message carries the SQL and the driver's own message, and never the bindings. The driver may quote a value in what it says (MySQL names a duplicate entry); that is kept, and the guide says so.
- A statement is retried on a new connection only when the old one was already closed before the statement was sent and no transaction was open. Anything that may have reached the server is reported, not repeated.
- A transaction that lost its session, or that MySQL rolled back whole as a deadlock victim (error 1213), fails its entire callback, enclosing ones included: every further command in it is refused until it unwinds, and the deadlock error is what leaves `transaction()`, so the caller can run the whole callback again. A message about such a loss never says what was or was not committed.
- A database is described under `database.connections`, by name, whether there is one or several; there is no flat form, and `database.dsn` is refused. A connection's `async` uses Crab's own MySQL driver (`Database\Mysql`) inside a worker; console commands stay on PDO. `options['ssl']` is mapped to PDO there only where PDO can keep the same policy, anything else is refused by name, and a session that asked for TLS and is not encrypted is refused.
- Code that needs the time asks for `Contracts\Clock\Clock` (or PSR-20's `ClockInterface`, which is bound to the same object, where a signature should accept any PSR clock) and never calls `time()`, `date()` or `new DateTime('now')` itself, so a test can hold the clock still with `Testing\FrozenClock`. A component that works standalone takes the clock as an optional argument.
- `Table` and `Column` collect what a migration says and hold no SQL; `SchemaGrammar` writes it, and a dialect subclass says only where its database differs, as with `Query` and `Grammar`. A new column type is added to `Table`, to both dialects and to the tests of both.
- A migration runs in a transaction only where the database can roll back a change to its tables; say so wherever that difference reaches the user.
- Two deployments never run the same migration. On MySQL `run()` and `rollback()` hold a named lock on one connection, and check they still own it before each migration and before returning. On SQLite each migration commits on its own and checks its record again inside `BEGIN IMMEDIATE`, skipping what another process finished. `status()` and `make()` take no lock. The wait is `database.migration_lock_timeout`, whole seconds, zero for no wait.
- A migration works through the `Schema` and connection it is given, so a pool of one is enough; one that takes another connection from the pool needs two.
- An application's databases are configured by name and held by `DatabaseManager`. Asking for the `Database` contract gives the default one, and `Database::connection($name)` another; do not bind a second database in the container under a name of its own. A connection is described by `driver`, `host`, `port`, `database`, `username` and `password`, and `DatabaseManager::dsn()` writes the data source name from them; a `dsn` given in their place is used as it is.
- The layers are built in order and each works without the one above it: pool, query layer, query builder, schema builder, migrator. Do not make a lower layer depend on a higher one. There is no model layer; see Scope.
- The query builder needs only the `Connection` contract. The one place a lower layer names it is `Connection::table()`, a single `new Query($this, $table, as: $as)`; nothing else in the pool or query layer may know it.
- `Query` collects what a statement says and holds no SQL; `Grammar` writes it, and a dialect subclass overrides only where its database differs. A new clause is state on `Query` and a method on `Grammar`, never SQL assembled in `Query`.
- In the builder, values are bound, names are quoted and operators are checked against a fixed list. Only methods ending in `Raw` take SQL as written, and every one of them takes bindings.
- A query inside another is written by the outer statement's grammar, in place, its values appended as its SQL is written, so the bindings stay in placeholder order at any depth. Rows read from a query are never a table to write to.
- A JSON path in a column name, `data->a->b`, is written into the SQL as a string, so each key is held to letters, digits, `_`, `-` and `[n]`; widen that only with a bound path. Paths are read, never written. Where a dialect's JSON differs from what a reader expects (MySQL's JSON null, its booleans), its grammar says so; the builder does not.
- `cursorPaginate()` refuses an order it cannot follow exactly: one that does not end with the unique column, one by an expression rather than a selected column or alias, one by a column not selected. It reads the query as a derived table so that an alias or a grouped column can be compared; keep that, rather than repeating expressions in the where. A cursor that does not decode to the order's fingerprint and values is `Contracts\Database\InvalidCursor`, a 422 through `Contracts\Http\HttpError`, never a first page in silence. A component that cannot depend on HTTP marks a client's mistake that way, never by extending `HttpException`.
- A builder method that runs a statement leaves the query unchanged. A mistake in building a query is thrown from the call that made it, and `update()` and `delete()` refuse a query whose join, order or limit they would have to drop.
- Database tests run on SQLite in the suite and on MySQL when `CRAB_TEST_MYSQL_DSN` is set; run both before changing `src/Database/`.
- SQLite is opened with a write-ahead log and a busy timeout, and its transactions begin with `BEGIN IMMEDIATE`: several processes write to the one file, and a transaction that reads before it writes would otherwise be refused at once when another writer is at work.

## Readability

- Crab is built for JSON APIs and to be read by people and AI agents alike. A file should be understandable on its own: declare parameter, return and property types everywhere, and prefer a named class to an array whose keys the reader must look up.
- Nothing happens that the code does not show: no hidden globals, no auto-discovery, no behaviour switched by a naming convention. Offer one way to do a thing, not two.
- A static name is allowed only for declaring what is fixed before workers start: `Route::get()` for routes and `Command::add()` for commands, each one line onto the current application, like `config()`. There is none for the request, the user, the container or any service, because a worker serves overlapping requests. Do not add another without the owner's agreement.
- An error message says what was wrong and what to do instead, so that a person or an agent can fix it without reading the framework.
- Write plain statements that read top to bottom. Name a value on one line and use it on the next; do not call the result of a `require`, nest closures to pass one value, or pack unrelated steps into one expression.
- A fluent chain is fine where each call is one named, typed step on its own line, as in `App::configure()->with...()->create()` and the query builder: the editor completes every step and the reader sees one thing per line.
- This matters most in what application developers see: the skeleton, the README examples and error messages.
- `php cua describe` is the application's description of itself for agents. Something an application declares (a route, a command, a server, a scheduled task, a listener) is shown there; when you add a kind of declaration, add it to `describe` in the same change. Its text form is the tested one (decision 11 in [ARCHITECTURE.md](ARCHITECTURE.md#decisions)); change its notation only by testing it on agents again.

## Helpers

- Global helpers exist only for process-scope values (`config()`, `env()`). There is no helper for the request, the authenticated user or the container.
- Call `env()` only inside configuration files; everything else reads `config()`.
- A global helper function lives in the `helpers.php` of the component it belongs to when it needs only that component (`env()` in `src/Config/helpers.php`). A helper that needs the running application lives in `src/helpers.php` (`config()`).
- Wrap each helper in `function_exists`, list its file under Composer's `files`, and keep it a thin call to a class method that works without the helper.

## Performance

- Code on the request path builds values on first use and avoids objects created per request. When changing `Http` or `Routing` request-path code, measure the per-request cost against the engine alone with JIT on, in the manner of `benchmarks/request-path.php`, and report it.
- Do not add an optimization that reuses parsed data across identical requests; that is a benchmark hack. Lazy work is fine.
- A worker-local cache reclaims expired entries even when their keys are never asked for again, and what a connection or task leaves in a map is removed on every way it can end.
- A caller waiting for exclusive use of a shared connection waits under its own cancellation and deadline; one that gives up leaves the queue, and one that abandons a turn it got returns it and any flow-control window it reserved.
- The HTTP client closes connection pools that have stayed idle, during later client activity, even for servers it never calls again; a failed attempt that borrowed nothing does not renew their idle time.

## Workflow

- Commit directly on `main`, without feature branches. Commit and push only when asked.
- PHP is formatted and linted by Mago (`composer format`, `composer format:check`, `composer lint`) with one `mago.toml` shared by every repository, differing only in paths. A default rule is turned off only in `mago.toml`, with a comment saying why. Mago's automatic fixes are reviewed and tested like any change: a loop whose condition does the work is not empty.
- A test of concurrency proves overlap or order with barriers and a diagnostic deadline, never a tight wall-clock window; elapsed-time bounds belong to timeout tests and benchmarks, with margins a loaded CI runner meets. A test double keeps production's serialization, validation and cleanup, and interchangeable stores share one set of contract cases. An exception test asserts outside the region whose exception it catches.
- A guide example that reads the time is tested with a clock deliberately different from wall time.
- A test fake records what production would have sent, captured at the serialization boundary when it is called, not the object it was given.
- When the README repeats a guide's example or promise, both change together, and an executable example is tested from its text. A generator's next-step hint uses current syntax and names the class or import it needs.
- A shell example in the guide stops at the first failed step (`set -e`); one that prepares a release migrates before it reloads, and one reload restarts HTTP, queue and schedule together.

## Application skeleton

- The skeleton is the separate repository `crabphp/crab`, beside this one, and reads the framework from `../framework` until there is a release.
- It stays minimal and readable at a glance: `app.php` describes the application, `cua` is the command line (`php cua dev`), and the folders are `routes/`, `app/Actions/`, `app/Providers/`, `config/`, `database/migrations/`, `storage/` and `tests/`.
- An application's `app/` has few folders, by where a class is used and not one for each kind: `Actions/` for every class with `handle()` (what a route points at, a job, a listener, a scheduled class), `Console/` for commands, `Http/` for what only a request meets (middleware, input classes), `Providers/`, and `Events/` for event objects. A folder is made when there are files for it, not before. Do not add `Jobs/`, `Listeners/`, `Middleware/` or `Commands/` to the skeleton, the sample or the guide.
- `storage/` holds what the application writes while it runs (logs in `storage/logs/`, the SQLite file, the file cache when its directory is set there, later uploads) and is never committed. Nothing the application needs in order to start lives there. A relative `log.path` is inside the application's base path. Add a folder to it only when a component that needs one is built.
- `app.php` is one `App::configure(__DIR__)` chain that names the providers and, in `withRouting(routes:, commands:)`, the route and command files, and ends in `create()`. The builder starts with the framework's provider and middleware lists, `App::PROVIDERS` and `App::MIDDLEWARE`, and finds nothing by convention. `App::configure()` applies the providers and, with a base path, takes `withEnv('.env')` and `withConfig('config', required: false)` on the application's behalf. An application names only its own and its packages' providers; `remove:` and `only:` change the framework's part. A new default needs the owner's agreement and is written where anyone can read it. A step takes one thing or a list. The route files declare with `Route::` and `Command::`, and no skeleton file uses a variable it did not define.
- When the framework changes how an application is written, change the skeleton, its README and its `AGENTS.md` in the same piece of work, and run its tests. The skeleton's `AGENTS.md` is what an agent working on an application reads first: keep every rule in it true, and keep it short.

# Engine conventions

- Use multiline docblocks for class, function, and member declarations; allow single-line docblocks only inside method or function bodies.
- Keep the engine core lightweight and compatible with PHP 8.4, using its modern features and a pure-PHP select backend by default; do not require Swoole, OpenSwoole, or similar runtimes, and keep native event backends optional.
- Build the engine as a powerful, general-purpose networking foundation first; design the minimal web and agent-facing layers separately later, keeping their dependencies and features outside the core.
- Include TCP, UDP, HTTP, and WebSocket servers in the required engine release scope; HTTP/WebSocket are engine protocol modules, while the later web framework remains separate.
- Prioritize performance with proven networking designs and reproducible measurements, while keeping extension points small and explicit.
- Keep reproducible HTTP and WebSocket benchmarks and repeat matched measurements when changing their performance-critical paths; report throughput, latency, errors, environment and limitations without claiming an unmeasured maximum.
- Nothing the engine catches is dropped. A `catch` that does not rethrow reports through `FailureReporter::report()`, or `Connection::reportFailure()` for a protocol owner; never a bare `catch (\Throwable)` and never `error_log()`. A client's malformed input is answered, not reported. Engine tests read `$this->reports`.
- The engine is written against its own `EventLoop` (an abstract class, whose `EventLoop::current()` is the process's loop) and `Suspension`. The scheduler is the engine's own `FiberEventLoop` in `src/Engine/EventLoop/`, with `StreamSelectEventLoop` as the default backend; `RevoltEventLoop` serves the native ev, event and uv backends. A loop method the engine needs is added to `EventLoop`, `FiberEventLoop` and `RevoltEventLoop` together.
- Name a type for what it is, in full: `EventLoop`, not `Loop`. One exception by the owner's choice: `Engine\Crab` is a named set of identical worker processes (a "worker group" elsewhere), named after the project. Do not name a class as the plural of another (`Loops`); put the behaviour on the type it belongs to. Evaluate the overhead of any change there and preserve PHP 8.4 compatibility.
- During the engine redesign, treat existing code and architecture as references; choose APIs, ownership boundaries, and dependencies from the requirements without preserving the current design for compatibility alone.
